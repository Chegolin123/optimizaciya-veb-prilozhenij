# Конспект — 3. Оптимизация серверной части

> Тема занятия из [таблицы курса](https://docs.google.com/spreadsheets/d/1mLdR4r9jjsBcKdaG77887BA6OdZc_tCmDNlfhJGdJfk/edit?gid=187801412).

## Зачем оптимизировать сервер

Клиентская вёрстка может быть идеальной, но если сервер отвечает медленно, страница «тормозит» всё равно. Ключевая метрика — **TTFB (Time To First Byte)**: время от запроса страницы до первого байта ответа сервера. Хороший TTFB — сотни миллисекунд; >1,5 с — проблема.

Клиент видит: TTFB + загрузка ресурсов + рендеринг = LCP.

## Из чего состоит серверная часть

- **Web-сервер** — nginx, Apache
- **Язык/рантайм** — PHP, Java, Node.js, Python
- **База данных** — MySQL, PostgreSQL
- **Файловое хранилище** — статика, изображения, бэкапы
- **Сеть и CDN** — канал, географически распределённые кэши

## База данных

| Приём | Суть |
|-------|------|
| Индексы | Ускоряют поиск строк по ключу (как указатель в книге); лишние/дублирующие индексы замедляют запись |
| EXPLAIN / профилирование | Разбор плана выполнения запроса — искать Full Table Scan |
| Нормализация | Разбиение данных по таблицам, устранение дублирования |
| Денормализация (точечно) | Дублирование данных ради скорости чтения (каунтеры, денормализованные справочники) |
| SQL-оптимизация | Выбирать только нужные поля, `LIMIT`, правильные `JOIN` вместо подзапросов |
| Пул соединений | Переиспользовать подключения к БД, а не открывать на каждый запрос |
| Кэширование запросов | Повторяющиеся SELECT — в кэш (Redis/Memcached) |

**Признак проблемы:** страница товара/каталога открывается дольше, чем главная; пики нагрузки «ложат» сайт.

## Web-сервер

- **Nginx** — статика отдаётся быстро, проксирование, балансировка
- **Рабочие процессы** — режется под число ядер CPU
- **Keep-Alive** — переиспользование TCP-соединений (без рукопожатий на каждый файл)
- **Сжатие** — gzip/Brotli для текстовых ответов
- **HTTP/2, HTTP/3** — мультиплексирование, параллельная загрузка ресурсов
- **Статика на CDN** — файлы отдаются из ближайшей к пользователю точки

## Кэширование

| Уровень | Что кэшируется |
|---------|----------------|
| Кэш страниц | Готовый HTML чаще всего меняющейся страницы |
| Кэш запросов | Результат тяжёлого SQL-запроса |
| Опкод (opcache) | Скомпилированный PHP-код |
| Браузерный кэш | Cache-Control / ETag (клиентская сторона, но задаётся сервером) |

Правило: **инвалидация кэша** — при изменении данных кэш сбрасывается, иначе пользователь увидит старое.

## Выбор хостинга (связь с [Конспект — 1.1. Основы разработки web-приложения](%D0%9A%D0%BE%D0%BD%D1%81%D0%BF%D0%B5%D0%BA%D1%82%20%E2%80%94%201.1.%20%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D1%8B%20%D1%80%D0%B0%D0%B7%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B8%20web-%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.md))

| Тип | Когда уместен |
|-----|---------------|
| Виртуальный хостинг | Небольшой сайт, общий сервер |
| VDS/VPS | Свой лимит CPU/RAM, полный контроль |
| Выделенный сервер | Крупный проект, «тяжёлые» сайты, нестандартные задачи |
| Co-location | Своё железо на площадке провайдера |

Оптимизация серверной части часто дешевле оптимизации железа: индексы и кэш дают +80% эффекта при отсутствии затрат.

## Мониторинг

- **Uptime** — доступность (провайдеры обещают 99.9%+)
- **Время ответа** — p50/p95/p99 (среднее — не показатель; важны «хвосты»)
- **Медленные запросы** — лог медленных SQL
- Ошибки 5xx, таймауты, очереди

## Термины

| Термин | Определение |
|--------|-------------|
| TTFB | Time To First Byte — время до первого байта ответа сервера |
| Индекс БД | Структура данных, ускоряющая поиск по таблице |
| EXPLAIN | Команда, показывающая план выполнения SQL-запроса |
| Окпаке / opcache | Кэш скомпилированного PHP-кода |
| CDN | Сеть доставки контента из ближайшей точки |
| Invalidtация кэша | Сброс кэша при изменении данных |
| N+1 запрос | Антипаттерн: SQL-запрос на каждый элемент коллекции вместо одного JOIN |
